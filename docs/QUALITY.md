# Проверки качества CopyNote

Для разработки нужны Windows amd64, PowerShell 7.2+, Node.js 22.13+ и Go.
В `go.mod` закреплён исправленный toolchain Go 1.26.8; язык исходников остаётся
Go 1.25. Go автоматически загрузит toolchain при первом запуске.

## Запуск

```powershell
# Установка закреплённых инструментов и npm-зависимостей.
pwsh -NoProfile -File tools/quality/setup.ps1

# Форматирование исходников. Этот режим не исправляет логику автоматически.
pwsh -NoProfile -File tools/quality/check.ps1 -Fix

# Все проверки, тесты, сборки и два коротких fuzz-прогона.
pwsh -NoProfile -File tools/quality/check.ps1 -Fuzz
```

Без `-Fuzz` выполняются те же проверки, кроме генерации новых входов для
fuzz-тестов. Их исходные примеры всё равно проверяет `go test`.
Для работы без сети можно явно передать `-SkipVulnerabilities`: это отключает
только npm audit и govulncheck. CI выполняет обе проверки безопасности.

Проверяется то, что отслеживает git. Черновик, лежащий в рабочей копии, не
оценивается и в режиме `-Fix` не переписывается; новый файл попадает в проверку
после `git add`. В конце запуска сценарий перечисляет то, что он пропустил.
Исключение — пакеты Go и каталог `web/`: компилятор, svelte-check, ESLint и Knip
видят в них все файлы, в том числе ещё не добавленные.

### Рабочая копия, выгруженная до появления `.gitattributes`

`.gitattributes` закрепляет LF, но git применяет это правило только к файлам,
которые записывает сам. В копии, выгруженной раньше при `core.autocrlf=true`,
остаются файлы с CRLF: форматирование их отвергает, а в `third_party`, где
преобразование отключено, они попали бы в коммит как есть. Проверка называет
число таких файлов и останавливается; `check.ps1 -Fix` один раз переводит их
в LF, не меняя остального содержимого.

### Инструменты

Бинарные инструменты, PowerShell-модуль, тестовые exe и кеш golangci-lint лежат
в игнорируемом `.quality/`. Установка не меняет глобальные инструменты. Кеши
модулей и сборки Go и кеш npm остаются обычными: собранное одним запуском
использует следующий, а CI сохраняет их между запусками.
Тестовые exe остаются в `.quality/test-bin`: это позволяет выполнять их при
политиках защиты, ограничивающих запуск новых exe из системного TEMP.

Версии Go-инструментов и PSScriptAnalyzer закреплены в
`tools/quality/versions.json`, npm-инструментов —
в `web/package.json` и `web/package-lock.json`. Архивы golangci-lint, actionlint
и PSScriptAnalyzer сверяются с SHA-256, записанными в том же `versions.json`:
список контрольных сумм, лежащий рядом с загрузкой, подменил бы тот же, кто
подменил саму загрузку. Без записанной суммы `setup.ps1` архив не скачивает,
поэтому при смене версии нужно внести и сумму нового архива, сверив её с
опубликованной издателем. Установленный инструмент повторно не загружается.

govulncheck собирает сам Go: модули проверяются по его базе контрольных сумм.
Если сборка не удалась (нет доступа к proxy.golang.org), `setup.ps1` предупреждает
и продолжает; на такой машине `check.ps1` запускают с `-SkipVulnerabilities`.

## Область анализа и исключения

- `third_party`, npm-зависимости, бинарные артефакты и `web/dist` не форматируются.
  Сборка обновляет отслеживаемый `web/dist/index.html`; CI проверяет его соответствие
  исходникам. `.gitattributes` закрепляет LF для исходников, сохраняя файлы
  `third_party` без преобразования строк.
- ESLint отвечает за корректность, Prettier — за оформление. Правила оформления
  ESLint, конфликтующие с Prettier, отключены через eslint-config-prettier.
- Staticcheck проверяет ошибки и упрощения (`SA*`, `S1*`). Имена констант Win32
  сохраняют соответствие Windows SDK; формальные требования к именам и сложности
  функций не заменяют проверку поведения.
- `LazyProc.Call` исключён только из errcheck: возвращаемый last-error может быть
  ненулевым при успехе. Обёртки Win32 проверяют результат по контракту каждой API.
  Намеренное игнорирование ошибок освобождения ресурсов обозначено явно.
- Отдельного `go vet` нет: те же анализаторы выполняет govet в составе
  golangci-lint. Форматирование проверяет `golangci-lint fmt` по списку файлов,
  поэтому под него попадают и файлы, исключённые из сборки условием
  (`tools/genicon`).
- golangci-lint анализирует код с тегом сборки `clipboard_real`. Иначе тест
  записи в настоящий буфер обмена не компилирует ни одна проверка, а объявления,
  нужные только ему, выглядят неиспользуемыми. Сам тест по-прежнему запускают
  вручную: он заменяет содержимое буфера.
- Пакеты Go берутся из `go list ./...` и ограничиваются каталогами с
  отслеживаемыми файлами: иначе в проверку попадают черновые пакеты и Go-код,
  который некоторые npm-пакеты кладут в `web/node_modules`.
- Перенос приложения выключен одной константой `relocationEnabled` в Go. Его
  код и интерфейс собираются и проверяются наравне с остальными, без исключений
  в Knip и без `nolint`. Prettier запускается из корня репозитория, а не
  npm-сценарием, поэтому он и его плагин отмечены в Knip явно. Экспорты,
  используемые внутри того же файла, не считаются мёртвыми.
- dependency-cruiser закрепляет зависимости TS-модулей состояния и действий.
  Полноту графа зависимостей компонентов Svelte проверяет Knip.

## CI

Windows CI выполняет те же `setup.ps1` и `check.ps1 -Fuzz`. Между запусками
сохраняются кеш модулей и сборки Go, кеш npm и установленные инструменты
(`.quality/bin`, `.quality/psmodules`, `.quality/installed`; ключ — содержимое
`versions.json` и `setup.ps1`). Вход, на котором fuzz-тест упал, прикладывается
к запуску как артефакт `fuzz-failures`.

## Проверка настоящего приложения

При изменениях поведения Win32/WebView2 после сборки используются сценарии
`tools/testinstance`. Они сохраняют четыре linker override, отдельные данные,
профиль WebView2, singleton, tray и autorun. Эти интерактивные сценарии не входят
в CI. Занятые ежедневным CopyNote глобальные горячие клавиши нельзя освобождать
ради теста; ограничения конкретного сценария описаны в README стенда.
При заблокированном экране проверки, которым нужны активное окно или настоящие
нажатия клавиш, помечаются как пропущенные, а не как отказавшие.
