# Принципы разработки CopyNote

DRY, KISS и SOLID служат понятности, надёжности и удобству изменения программы.
Сохранение пользовательских данных, совместимости и важного поведения имеет
приоритет над формальным соответствием подходу. Рефакторинг должен решать
конкретную проблему и иметь проверяемый результат.

## DRY: одно правило — один источник

- Валидация записей и настроек, значения по умолчанию и чтение JSON принадлежат
  `internal/model`. Загрузка данных, импорт и миграция старого файла настроек
  используют одинаковые правила. Отсутствующее поле и явные `false`, `""`, `null`
  различаются; новые поля сохраняют поведение старых установок.
- Запись и публикация снимка принадлежат `Service`. Сначала успешно сохраняем
  данные, затем меняем состояние в памяти. Сохранение настроек, их изменение из
  Go и импорт используют общий путь транзакции и уведомления.
- Повторяемую механику выделяем в небольшие функции: привязки моста, очередь
  операций, вычисление позиции окна. Сходство синтаксиса само по себе не повод
  объединять операции с разными жизненными циклами.
- Версия программы определяется только в `internal/version/version.go`.
  Типы Go и TypeScript отражают общий контракт моста; не создаём генератор или
  универсальную схему только ради устранения этого небольшого повтора.

## KISS: минимальное достаточное решение

- Предпочитаем прямой код и небольшие функции. Добавляем абстракцию, если она
  устраняет существующий повтор, изолирует внешнее действие или упрощает
  проверку. Возможные будущие требования не оправдывают слои и фреймворки.
- Модуль имеет понятную задачу. Размер файла — сигнал для изучения, а не лимит:
  связанную логику сохраняем вместе, независимые задачи разделяем.
- Сохраняем привычные интерфейсы при внутреннем разделении. Компоненты получают
  действия через `state.svelte.ts`; модули действий обращаются к общему
  `appState.svelte.ts` напрямую и не импортируют фасад обратно.
- Комментарии объясняют причины, ограничения Windows и намеренные исключения.
  Изменяя поведение, обновляем описание рядом с кодом и руководство проекта.

## SOLID: ясные обязанности и узкие зависимости

- **SRP:** модель проверяет данные; storage читает и атомарно пишет файлы;
  Service выполняет бизнес-операции и транзакции; адаптеры clipboard/autorun/tray
  работают с Windows; мост соединяет приложение и интерфейс. Фронтенд разделяет
  записи, настройки, обновления и перенос приложения.
- **OCP:** выносим изменяемую политику или внешнее действие в точку подмены при
  реальной необходимости. Для добавления небольшой функции допустимо изменить
  существующий код; система плагинов для гипотетического расширения не нужна.
- **LSP:** подмена зависимости сохраняет контракт, включая ошибки, порядок
  действий и результат. Не вводим наследование ради применения принципа.
- **ISP:** зависимости описываем только нужными операциями. Для одиночного
  действия достаточно функции; крупный интерфейс «на все случаи» не нужен.
- **DIP:** внешние операции Service передаются через `service.Dependencies`;
  производственные значения по умолчанию собраны отдельно. Тесты подменяют
  часы, хранилище, буфер обмена и автозапуск без обращения к реальной установке.

## Согласованность и обработка отказов

- Настройки, импорт/экспорт и изменение горячей клавиши проходят через одну
  очередь фронтенда. Патч объединяется с последним успешным снимком при начале
  операции. Отказ одной операции не блокирует следующие.
- Горячая клавиша сначала регистрируется в Windows, затем сохраняется. При
  отказе записи восстанавливается предыдущая комбинация. Ошибки записи и
  отката видны пользователю. Восстановление автозапуска выполняется аналогично
  в сервисной транзакции.
- Побочный эффект после успешной записи не означает, что запись не состоялась.
  Не откатываем успешный снимок из-за более поздней ошибки интерфейса.
- После успешного сохранения, изменения или импорта настроек уведомляем трей.
  `SettingsSaved` вызывается под блокировкой сервиса: callback должен быстро
  поставить работу в очередь, не обращаться обратно к Service и не ждать UI.
- Отмену диалога отличаем от успеха; повреждённые файлы не сбрасываем молча.
  Сохраняем атомарную запись, резервную копию и проверку импорта до изменения.

## Намеренные ограничения и исключения

- WebView2 при скрытии остаётся активным: окно паркуется за экраном. Не заменяем
  это на `SW_HIDE`. Подготовка DOM и размера перед показом, поколения анимаций,
  DPI, фокус и незавершённые модальные формы сохраняются при рефакторинге.
- Трей работает на отдельном OS-потоке; изменения окна идут через `w.Dispatch`.
  При перезапуске ребёнок ждёт завершения родителя перед созданием WebView2,
  а родитель после запуска ребёнка сразу завершает выход.
- В `EntryList` два блока списка используют общий snippet: анимация только без
  фильтра, обычный список при поиске. Это защищает поиск по большому списку от
  лишних измерений DOM. Не объединяем блоки ради внешнего уменьшения повтора.
- Флаги с инвертированным смыслом сохраняют прежние значения по умолчанию.
  Состояния ожидания трея и подготовки окна имеют разные обязанности.
- Перенос приложения временно отключён. Сохраняем реализацию и отключение,
  пока отдельная задача явно не предусматривает его включение.
- Локальные зависимости `third_party` не переписываем в ходе такого рефакторинга.

## Проверка изменений

1. Опишите проблему, ожидаемое поведение и важные ограничения.
2. Сделайте минимальное связное изменение. Добавляйте тесты для существенных
   сценариев и отказов, особенно записи, отката и конкурирующих операций.
   Тесты проверяют поведение, а не повторяют реализацию.
3. Для логики Go выполните `go test ./...` и `go vet ./...`; для фронтенда —
   `npm run check`, `npm test`, `npm run build` из `web/`. Отслеживаемый
   `web/dist/index.html` должен соответствовать исходникам; проверьте сборку Go.
4. Если изменение затрагивает поведение Win32/WebView2, выберите относящиеся к
   нему сценарии `tools/testinstance`. Используйте изолированные данные, профиль
   и все четыре linker override, включая прежнее имя
   `copynote/internal/service.autorunValueName`. Не затрагивайте ежедневный
   экземпляр, его автозапуск и горячие клавиши.
5. Просмотрите diff: понятность, отсутствие ненужных слоёв, совместимость,
   актуальность документации. В результате укажите проверки и их ограничения.
